============================================================
1. RESEARCH QUESTION
============================================================

The final research question is:

"Does prospective execution/lifecycle type provide incremental predictive
value for individual GPU/ML job runtime beyond other prospective
information?"

For the Alibaba ASI dataset specifically:

"Does job_type_public improve individual execution-duration prediction
beyond the prospective controls available in ASI, and does that
improvement persist under stronger generalization settings such as
unseen workloads?"

This is a PREDICTIVE / INFORMATION-CONTRIBUTION study.

It is NOT a causal study.

Formal comparison:

    M0: T_hat = f(X)

    M1: T_hat = f(X, O)

where:

    T = individual execution runtime

    O = prospective execution/lifecycle type

    X = other legitimately available prospective information

The scientific quantity of interest is the incremental predictive value
of O.

============================================================
3. WHY THIS QUESTION SURVIVED PRIOR AUDITING
============================================================

Several earlier directions were investigated and rejected.

A. Original "experimental objective" idea

The original concept involved debugging, evaluation, HPO, final training,
etc.

Public traces generally did not expose a sufficiently clean,
documented, prospective objective label.

The project was narrowed rather than stretching other variables into
that construct.

B. AcmeTrace

AcmeTrace had attractive labels such as:
    Eval
    Pretrain
    SFT
    MLLM
    Debug
    Other

However, correspondence with an author established that released
categories were determined using post-execution information, especially
job-name hints and job duration.

Thus the released label effectively involved:

    type = g(job-name hints, duration)

Using it to predict duration would introduce target leakage.

AcmeTrace was rejected.

C. PAI

PAI exposes useful semantics but primarily L3/L4/task-role information,
not a sufficiently clean prospective job-level L1 objective.

Do not stretch PAI variables into L1.

D. Completion-aware / scheduler-feedback direction

We investigated delayed runtime-label availability and
scheduler-dependent feedback loops.

Prior-art auditing showed substantial precedent for event-driven
runtime updates and related feedback mechanisms.

That direction was killed.

E. Generic "semantics improves runtime prediction"

This is too broad and crowded.

Prior systems already use application type, scripts, model/configuration
information, workload identity, etc.

The unresolved question is narrower:

Does prospective lifecycle type provide incremental predictive
information after legitimate controls and under strong generalization?

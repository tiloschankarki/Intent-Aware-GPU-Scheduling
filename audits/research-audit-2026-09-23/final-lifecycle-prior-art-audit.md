# Final prior-art audit: prospective lifecycle type and GPU-job runtime

Audit date: 23 September 2026. Search cutoff: material publicly discoverable by that date, not the remainder of September. This report supersedes earlier conclusions about the narrower, different construct “experimental objective.”

## Decision

**LOCK THE QUESTION.** Under the stipulated prior-art criterion, I did not find a verified study adequately isolating the incremental runtime-predictive contribution of prospective GPU/ML execution/lifecycle type beyond strong conventional, planned-scope, model, configuration, and history controls.

This is a bounded negative search result, not proof that no such publication exists. It is not a finding that lifecycle metadata is new, that its usefulness has never been investigated, or that the resulting experiment would meet a top conference's contribution threshold. Those stronger claims are unsupported.

The conceptual territory is crowded. PolarisProfiler already connects prospective task-role metadata to duration prediction. Older HPC work already includes batch/interactive mode in runtime prediction and selects combinations of predictive attributes. Menear already performs an application-information inclusion/exclusion experiment. Combining these precedents makes “add one type column and report lower error” a weak contribution even without an exact duplicate.

## What was tested by this audit

The target is individual job execution duration T, predicted from information available at a specified prediction time. O is declared execution/lifecycle type: training, development, evaluation, online/offline inference, and related modes. X includes conventional scheduler fields and available L2 planned computational scope, L3 model/application semantics, and L4 configuration/recurrence identity.

The distinguishing experiment compares a suitably trained predictor using X with one using the same X plus O, on identical prospective evaluation cohorts. It must not silently remove strong baseline controls, introduce completed-job information for the job being predicted, or call a profile-classifier explanation an isolated duration-prediction ablation.

Categories used below:

- **A:** verified prospective L1 input and an incremental L1 test.
- **B:** explicit lifecycle/execution-type input without the required isolated test. Mixed task-role fields and uncertain provenance are qualified.
- **C:** lifecycle information used for characterization or scheduling, without this duration-prediction test.
- **D:** conventional features and/or L2/L3/L4 semantics; no established explicit L1 test.
- **E:** retrospective category, unsuitable as prospective O.

“Not established” is not a claim that something is absent from every implementation. “Methods inspected” refers to the relevant method/evaluation sections, not reproducing a paper's experiments. Code inspection is identified separately.

## ASI's own contribution and public-data feasibility

[ASI, OSDI 2026](https://www.usenix.org/system/files/osdi26-li-suyi.pdf) §3.1 explicitly supports user-provided application metadata; its execution-time distributions (Fig. 7) are characterization. I found no model comparing individual-duration prediction with and without job type, no corresponding feature ablation, and no evaluation feeding such a learned duration predictor into IPC or SpotGPU. Those scheduling systems do not supply the missing conditional test merely because they use workload information.

The [public schema](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-gpu-v2026/docs/schema.md) supports only **part** of the proposed experiment:

| Requirement | Public evidence | Consequence |
|---|---|---|
| O | `job_type_public`: training / online_inference / offline_inference / dev / other / unknown | Real broad lifecycle construct; not merely model family. |
| L3 | `model_type_public`: coarse public buckets | Controls broad family, not exact architecture or model size. |
| L4 | Nullable `workload_id`, shared by multiple pods | Useful identity proxy; not certified exact configuration identity. |
| Resources | GPU requests/type, priority; hourly CPU request and accelerator-memory request | Several meaningful controls exist. Assigned hardware is not automatically known at submission. |
| User/history | No public user/tenant/organization field; histories may be derived by workload only | Cannot claim the stipulated strong user/history control set is fully observed. |
| L2 | No released epochs/steps/token budget/trial count in this schema | Cannot establish incremental value beyond measured planned scope from ASI alone. |
| Target | `duration_hours` is derived from observed execution samples; execution summary is pod/span-oriented | Must establish censoring, resolution and termination semantics before calling it complete job runtime. |
| Time | Relative hourly partitions; execution summary lacks an explicit submission timestamp | First observation need not be submission. Prospective evaluation requires a justified temporal reconstruction. |

Schema facts above are documentation evidence, not a completed statistical audit of the entire raw release. My methodological inference is that ASI alone cannot support the full strongest claim as currently worded. It can support a more limited available-controls comparison if the target and time reconstruction pass validation. Reporting that limitation is not a new research direction or a rescue; it is the difference between an executable regression and the proposed scientific test.

Online service residence time, a notebook session's lifetime, and a finite training run's completion time have different termination mechanisms. A pooled error reduction may reflect this distinction, missing planned work, administrative termination, or observation-window boundaries. It does not automatically establish useful prediction of completed computational work. Likewise, gains beyond coarse model labels do not prove gains beyond exact model/configuration/scope.

If workload identity nearly determines lifecycle type, there may be little within-identity variation. That does not prohibit an out-of-sample predictive comparison, but it limits conclusions about an independent lifecycle signal and makes seen/unseen-workload results essential. Histories must contain only outcomes completed before the prediction time. A chronological split alone does not enforce that rule.

## Access limits and corrections

The scoped search and reporting pass is finished. **A fully exhaustive full-text clearance is not established.** Remaining limits include the inaccessible full Liquid proceedings paper (partly resolved through code), ATLAS paper (resolved at notebook-feature level), the MIT HPCA PDF, the paywalled Iftekhar/Mishra chapter, and some older HPC sources available only through indexed primary text or citation lineage. GradSched's type provenance remains unknown. No lack of access is counted as evidence of absence.

Earlier statements requiring correction:

1. Broad “execution type has not been used for runtime prediction” is untenable: Smith and PolarisProfiler provide precedent.
2. Liquid cannot be dismissed solely as resource prediction: the artifact contains a duration-prediction path.
3. Menear's application ablation is real, but application identity is not automatically lifecycle type.
4. The ASI paper supplies stronger metadata-provenance evidence than earlier schema-only assessments recognized. It does not supply missing planned-scope/user fields or certify every historical snapshot's submission-time state.
5. “No L1-only ablation located” is not equivalent to “no prior work studies feature contribution.” Smith and rough-set methods do evaluate feature selection; PolarisProfiler explains classifier contributions.

## What the result means for the one-week project

**Research novelty:** the exact strong conditional GPU/ML question survives this search. First-use and broad semantic-prediction claims do not.

**Feasibility:** a one-week, reproducible pilot may be feasible with locally available manageable data. The full claim is not presently supported by ASI's documented public fields. Missing planned scope and user identity cannot be repaired with a better regressor. Target/provenance validation is a prerequisite, not optional cleanup.

**Conference merit:** there is no evidence yet for an OSDI/NSDI/SOSP/MLSys-level contribution. A question surviving a duplicate search does not meet that bar. A modest improvement after adding a familiar categorical variable to one new trace is unlikely to be enough. No honest audit can promise a defensible top-tier paper in one week before the actual effect, its robustness, and its systems significance are known.

**Strongest direct prior art:** none verified for the stipulated complete L1 incremental test.

**Strongest near miss:** PolarisProfiler and its extended manuscript for GPU/ML duration prediction with role-bearing metadata; Smith et al. for execution-mode prediction with historical feature selection. Menear is the closest explicit semantic inclusion/exclusion methodology.

**Exactly untested in the inspected evidence:** a clean prospective L1 inclusion/exclusion comparison for individual GPU/ML duration with strong conventional/L2/L3/L4 controls, valid completed histories, and credible out-of-sample evaluation.

**Main remaining novelty risk:** the claimed contribution may be only a missing ablation of an already familiar feature idea; inaccessible or insufficiently documented implementations may also contain a closer experiment. The main empirical risk is separate: available controls and duration labels may not identify the intended comparison.
